FUNDA LOG · 02 / 07 from building a funda-question generator

Read the error body, not the status code

Every call to the model came back 429. I diagnosed it four times before I read a single response body. All four diagnoses were wrong.

The setup is plain. A pipeline calls glm-4.5-air thousands of times, and it started failing on everything. HTTP 429 means too many requests, so I treated it as throttling and the retry logic did what retry logic does: exponential backoff, doubled on rate limits, up to 30 seconds a wait, five retries per call.

In order, the theories were heavy use, four concurrent processes each honouring an in-process cap of four, a concurrency breach, and a per-process semaphore that couldn't see the other processes. None of that was stupid. I'd measured this provider's limits earlier: glm-4.7 handled two concurrent requests fine, gave back 429s on half of them at three, and on 80% at five. The concurrency theory had data behind it. It was just aimed at the wrong problem.

What the response actually said:

{"error":{"code":"1113","message":"Insufficient balance or no resource package. Please recharge."}}

The account was empty. The status code is 429 whether the server is saying "slow down" or "you have no money", and nothing in my stack had ever opened the body to check which.

The retries were the cheap part: five of them at up to 30 seconds each, against an account that could never have succeeded. The expensive part was what got recorded. Two experiments logged results of 0 out of 8. They were really 0 out of 8 calls that reached the model. One got written up as a dead end and closed.

The tell had been sitting there. The clean arm of that experiment also scored 0/8. Identical zeros in both arms means nothing ran. I'd also been bitten by the cousin of this earlier, when a 429 got stored as "the model answered wrong" and dragged a measured hit rate on trivia down to 0.31 when it should have read about 0.52.

◆ to fill in before publishinghow long this ate, and which of the four theories you were most sure about.

The fix is a separate exception class, ProviderExhausted, raised on the first call when the body contains the provider's own wording ("insufficient balance", "no resource package", the 1113 code). A transient 429 still retries. I checked both directions: a throttle retries, an empty account stops immediately.

About an hour after that commit I found why the account was empty in the first place. I had a GLM Coding subscription, and it covers /api/coding/paas/v4/. Every call in the project had been going to /api/paas/v4/, which bills from a separate pay-as-you-go balance. Same key, same models, wrong URL. The subscription had been paying for an endpoint I never called. (The OCR endpoint isn't covered by the subscription at all, and fails on both.)

I wrote a design doc for the rest. One registry for providers instead of provider knowledge scattered across six files. Limits that nest, because a per-model semaphore can't express "the account is empty." Roles instead of model names, with some roles frozen because their calibration depends on a specific model and others free to fall back. A health state shared on disk so one process finding an empty account spares the others. A cross-process token bucket. All of that is on paper and marked "design, not built." What's in the code is the 429 split, plus the concurrency caps.

What each response should trigger (the first two rows and the last are in the code, the rest are in the doc):

the response sayswhat to do
429, throttle wordingback off, retry the same model
429, balance or quota wordingmark the provider dead, stop
404, model not foundfail loudly, never fall back silently
401 or 403fail loudly
5xx, timeoutretry
output cut off at max_tokensraise, never retry (it will cut off in the same place)

The last row is its own story. Thinking tokens come out of the same budget as the answer, and I lost three slide transcripts that way before the code learned to raise instead of returning a shorter string.
